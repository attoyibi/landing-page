Clean Code: Prinsip Menulis Kode yang Mudah Dibaca

Kode dibaca jauh lebih sering daripada ditulis. Anda sendiri, enam bulan dari sekarang, adalah pembaca yang paling sering lupa konteks. Clean code bukan soal gaya yang indah, melainkan soal mengurangi waktu yang dibutuhkan orang lain (dan Anda) untuk memahami dan mengubah kode dengan aman.

Oleh Muhammad Muchson Attoyibi·28 Oktober 2026·2 menit baca

Mengapa kode yang "jalan" belum cukup

Program yang berjalan hari ini akan diubah besok: fitur baru, bug, aturan bisnis berubah. Bila kodenya sulit dibaca, setiap perubahan menjadi mahal dan berisiko. Itulah sebabnya tim profesional menilai kode dari dua sisi: benar dan mudah diubah.

1. Nama yang menjelaskan maksud

Nama variabel dan fungsi adalah dokumentasi paling murah. Nama yang baik menjawab: ini apa, untuk apa.

# Sebelum
d = 7
def calc(a, b):
    return a * b * 0.11

# Sesudah
BATAS_HARI_RETUR = 7
TARIF_PPN = 0.11

def hitung_ppn(harga_satuan, jumlah):
    return harga_satuan * jumlah * TARIF_PPN
  • Gunakan kata benda untuk data (pesanan, total_bayar) dan kata kerja untuk fungsi (kirim_email, hitung_diskon).
  • Hindari singkatan pribadi seperti tmp2, dt, flg.
  • Angka "ajaib" seperti 0.11 atau 7 diberi nama konstanta.
  • Boolean dinamai seperti pertanyaan: sudah_bayar, is_aktif.

2. Fungsi kecil yang melakukan satu hal

Fungsi yang panjang biasanya mengerjakan beberapa hal sekaligus: memvalidasi, menghitung, menyimpan, mengirim notifikasi. Pecah menjadi fungsi-fungsi dengan nama yang menjelaskan langkahnya.

def proses_pesanan(pesanan):
    validasi(pesanan)
    total = hitung_total(pesanan)
    simpan(pesanan, total)
    kirim_konfirmasi(pesanan.email, total)

Fungsi utama di atas bisa dibaca seperti daftar langkah. Detail tiap langkah ada di fungsinya masing-masing.

3. Keluar lebih awal, kurangi sarang

# Sebelum: bersarang tiga tingkat
def bisa_checkout(user, keranjang):
    if user:
        if user.aktif:
            if keranjang:
                return True
    return False

# Sesudah: guard clause
def bisa_checkout(user, keranjang):
    if not user or not user.aktif:
        return False
    return len(keranjang) > 0

4. Komentar untuk "mengapa", bukan "apa"

Kode yang jelas sudah menjelaskan apa yang dilakukan. Komentar paling berharga menjelaskan mengapa: alasan bisnis, keputusan yang tidak terlihat, atau jebakan yang pernah terjadi.

# Buruk: mengulang kode
i += 1  # tambah i dengan 1

# Baik: menjelaskan alasan
# Bank mitra menolak transfer di atas 50 juta per transaksi,
# jadi pembayaran besar dipecah.
for bagian in pecah_nominal(total, 50_000_000):
    transfer(bagian)

5. Jangan ulangi diri sendiri, tetapi jangan terburu-buru

Prinsip DRY (Don't Repeat Yourself) mengajak kita menyatukan logika yang sama di satu tempat. Namun dua potong kode yang kebetulan mirip belum tentu logika yang sama. Banyak engineer memakai aturan praktis "tiga kali": baru diekstrak menjadi fungsi bersama ketika pola yang sama muncul ketiga kalinya.

Contoh lengkap: merapikan satu fungsi

Cara menerapkan di tim tanpa drama

  1. Aturan pramuka: tinggalkan kode sedikit lebih rapi daripada saat Anda menemukannya. Cukup satu nama yang diperbaiki.
  2. Otomatiskan gaya: pakai formatter (Prettier, Black, Laravel Pint) dan linter (ESLint, Ruff) agar debat spasi dan tanda kutip hilang.
  3. Sepakati sedikit aturan tertulis di README atau CONTRIBUTING, bukan puluhan.
  4. Refactor dengan tes. Tanpa tes, merapikan kode bisa diam-diam merusak perilaku.

Tanya jawab

Apakah clean code membuat program lebih lambat?
Hampir tidak pernah berarti. Fungsi kecil dan nama panjang tidak memengaruhi kecepatan secara nyata pada bahasa modern. Optimasi dilakukan setelah ada pengukuran.
Buku apa yang sebaiknya dibaca?
Clean Code (Robert C. Martin) dan Refactoring (Martin Fowler) adalah dua rujukan klasik. Baca dengan kritis; tidak semua aturannya cocok untuk semua bahasa.
Bagaimana dengan kode lama yang sudah berantakan?
Jangan menulis ulang semuanya. Rapikan bagian yang sedang Anda ubah, dan tambahkan tes sebelum mengubah perilaku.
