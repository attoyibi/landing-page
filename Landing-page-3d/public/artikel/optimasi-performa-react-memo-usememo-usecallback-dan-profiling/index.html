Optimasi Performa React: memo, useMemo, useCallback

Banyak orang mengoptimasi React dengan menaburkan useMemo dan useCallback di mana-mana, lalu heran mengapa tidak ada bedanya. Optimasi yang efektif dimulai dengan mengukur dan memahami mengapa render terjadi. Sering kali perbaikan terbaik bukan memoisasi, melainkan menata ulang tempat state berada.

Oleh Muhammad Muchson Attoyibi·30 Oktober 2026·3 menit baca·Tingkat: Lanjut

Sebaiknya sudah paham: useState, useEffect, props

Tujuan belajar

Setelah membaca dan mencoba materi ini, Anda mampu:

  • menjelaskan kapan dan mengapa komponen dirender ulang
  • membedakan render dari pembaruan DOM dan mengapa render murah itu normal
  • memakai React.memo, useMemo, dan useCallback pada tempat yang tepat
  • memperbaiki masalah dengan memindahkan state dan komposisi
  • mengukur dengan Profiler sebelum dan sesudah mengoptimasi

Kapan sebuah komponen dirender ulang

  • State komponen itu berubah.
  • Induknya dirender ulang (dan komponen tidak dibungkus memo).
  • Context yang dibacanya berubah.

Render adalah memanggil fungsi komponen untuk menghitung JSX; hanya bila hasilnya berbeda React menyentuh DOM. Render ulang yang menghasilkan keluaran sama itu murah dan wajar. Optimasi baru perlu bila render menjadi lambat (pekerjaan berat per render) atau terlalu sering pada pohon besar.

Mulai dari pengukuran

Pertama ukur. Buka React DevTools → Profiler, rekam interaksi yang terasa lambat, lalu lihat komponen mana yang memakan waktu dan mengapa ia dirender. Mengoptimasi tanpa mengukur sering menambah kerumitan tanpa manfaat.

Perbaikan pertama: pindahkan state ke bawah

Bila state yang cepat berubah (misalnya isi kotak ketik) berada di komponen besar, seluruh anaknya ikut dirender. Pindahkan state ke komponen kecil yang benar-benar memakainya.

React.memo: lewati render bila props sama

React.memo(Komponen) membuat React melewati render ulang bila props sama dibandingkan sebelumnya (perbandingan dangkal dengan Object.is). Perhatikan jebakannya: objek, array, dan fungsi yang dibuat di dalam komponen induk selalu "baru" pada setiap render.

useMemo dan useCallback: menyimpan hasil antar render

HookMenyimpanPakai bila
useMemo(() => hitung(a, b), [a, b])Hasil perhitunganPerhitungan benar-benar mahal, atau agar objek/array stabil sebagai props atau dependency

React Compiler

React Compiler (alat build dari tim React, kini tersedia dalam rilis stabil) dapat menambahkan memoisasi otomatis pada waktu kompilasi, sehingga Anda tidak perlu menulis useMemo dan useCallback secara manual di banyak kasus. Tetap saja, pemahaman tentang render, state yang diletakkan dengan baik, dan pengukuran tidak tergantikan.

Latihan mandiri
1. Kotak ketik membuat tabel besar lambat. Beri dua perbaikan tanpa memo.
Pindahkan state kotak ke komponen sendiri; atau gunakan useDeferredValue/debounce untuk nilai yang dipakai tabel.
2. Kapan useCallback tidak berguna?
Bila fungsi tidak dikirim ke komponen memo dan tidak menjadi dependency efek; ia hanya menambah kerumitan.
3. Mengapa menyimpan perhitungan murah di useMemo bisa lebih lambat?
useMemo sendiri punya biaya (menyimpan dan membandingkan dependency); untuk pekerjaan kecil biayanya melebihi manfaat.
4. Apa fungsi key pada pengoptimalan daftar?
Key stabil membuat React memindahkan elemen alih-alih membuang dan membuat ulang, menjaga state dan mengurangi pekerjaan DOM.
Coba kerjakan dulu sebelum membuka jawaban.
Ringkasan
  • Render murah itu normal; optimasi perlu bila lambat atau terlalu sering pada pohon besar.
  • Ukur dengan Profiler, lalu coba pindahkan state ke bawah dan komposisi lebih dulu.
  • React.memo, useMemo, useCallback bekerja bila props stabil dan pekerjaan memang berat.
  • Virtualisasi untuk daftar panjang, code splitting untuk bundel besar; React Compiler dapat mengotomasi memoisasi.

Tanya jawab

Apakah semua komponen sebaiknya dibungkus memo?
Tidak. Pembungkusan sembarangan menambah kerumitan dan biaya perbandingan; pakai di titik yang terbukti bermasalah.
Apa itu useDeferredValue?
Hook untuk menunda pembaruan bagian UI yang berat agar input tetap responsif; nilai "tertunda" menyusul setelah render mendesak selesai.
Bagaimana menganalisis ukuran bundel?
Gunakan plugin visualisasi (misalnya rollup-plugin-visualizer untuk Vite) untuk melihat paket yang memakan ruang dan pertimbangkan impor dinamis.
